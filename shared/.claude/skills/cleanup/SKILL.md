Handle the cleanup bead described in your bundle. This skill is for beads labeled `spex:cleanup` — work generated by `spex apply` when a component was removed from the spec but its code had already shipped. Your job is **removal**, not implementation.

## Preconditions (already done for you)

The deterministic prelude (`start-cleanup <bead-id>`) has run before this skill — the dca entrypoint runs it automatically; in an interactive session, run it yourself first. It has already:

- synced from `origin` and created your `cleanup/<component>` branch off `origin/<default>`,
- guarded the bead (carries `spex:cleanup`, status `open`/`ready`, signing key present),
- verified the **predecessor** (the `blocks:<old-bead-id>` dependency) is **closed** — its code has shipped, so there is something to remove,
- claimed the bead (`status in_progress`) with a **signed** commit on the branch,
- written a bundle to `$HARNESS_DIR` (default `${XDG_RUNTIME_DIR:-/tmp}/harness`): `CONTEXT.md` (bead + predecessor) and `bundle.env` (`BEAD_ID`, `BRANCH`, `PREDECESSOR`).

If no bundle exists, the prelude has not been run — stop and run `start-cleanup <bead-id>` first.

## Scope of removal

Get the removal scope from:

1. **Predecessor bead** — `br show <PREDECESSOR> --json` (id is in `bundle.env`). Its title gives you the component name (e.g. `apply: ProposalTagger`); its description describes what the component did — that's what you are removing.
2. **Proposal** — read the bead's `spec_proposal:<ref>` label, then open `spec/proposals/<ref>.md` to understand why the component was removed and what, if anything, replaces it. The proposal often names the replacement mechanism so you can verify the intended end state.

If the predecessor or proposal reference is missing, stop — the cleanup bead lacks traceability and you should not guess.

## Workflow (Removal)

1. **Identify the code to remove.** Find every file, function, struct, test, import, and reference that ties back to the removed component. Use the component name from the predecessor bead's title as your anchor:

   ```bash
   # Case-insensitive + identifier-level hits (whole-word with snake / camel / kebab variants)
   git grep -niE '(proposal[_ -]?tagger|ProposalTagger)' -- ':!.beads' ':!spec' ':!*.md'

   # Spec history — files that were deleted by the proposal's merge (context only, do not edit)
   git log --oneline --diff-filter=D -- 'spec/<module>/arch_<name>.md' 'spec/<module>/impl_<name>.md'
   ```

   Record every hit. Typical categories:
   - Core implementation file(s) (e.g. `apply/proposal_tagger.go`)
   - Direct unit test file(s) (e.g. `apply/proposal_tagger_test.go`)
   - Usage sites: constructors, wiring (look for the struct name or constructor function in `apply/run.go`, `cmd/spex/*.go`, etc.)
   - Imports that become unused after the removal
   - Test fixtures or setup helpers that only existed for this component
   - Documentation references outside of git history (e.g. README, `docs/`)

2. **Remove it.** Delete the implementation and test files. Update every usage site to no longer reference the component — most commonly removing a call site or struct field. Do not add backward-compatibility shims or fallback stubs.

3. **Fix the resulting compile errors.** If removing the component leaves orphaned callers, those callers must either be removed too, or (if they remain valid) reshaped to use whatever replaced the component. The proposal tells you which.

4. **Remove obsolete tests.** Tests that exercised only the removed component are deleted. Tests whose coverage shifts to the replacement mechanism should be updated to call the new code path, not deleted — only drop tests that become tautological.

5. **Do NOT write new tests.** Cleanup is removal. If you find yourself authoring a new test to prove "the component is gone", stop — a passing `go build ./... && go test ./...` with zero references to the component is the proof.

6. **Completion gate** (see below). Do NOT proceed until every item passes.

7. **Commit and push.** Commits must be signed; do NOT bypass signing. Commit message pattern:

   ```
   <bead-id>: remove <component-name> (<module>)

   <1-2 sentences on why the component was removed, per the proposal>
   ```

   Do NOT close the bead (review closes it) and do NOT push to the default branch.

8. **Open a PR** using `.github/pull_request_template.md`. Body should include the cleanup bead ID, the predecessor bead ID, and the proposal reference.

9. **Link the bead:** `br update <bead-id> --external-ref "PR#<number>"`, commit `.beads/issues.jsonl`, push.

## Completion Gate

Before committing, verify ALL of the following:

1. **Zero identifier references.** Run:

   ```bash
   git grep -niE '<component-identifier-patterns>' -- ':!.beads' ':!*.md'
   ```

   Zero hits outside git history = done. If any remain, either remove them or explain why they are unrelated false positives (e.g. a library function with a coincidentally similar name).

2. **Build clean.** `go build ./...` succeeds. `go vet ./...` reports nothing.

3. **Tests green.** `go test ./...` passes. Test count should drop (you removed at least the component's own tests); if it stayed the same, check whether you missed the test file.

4. **No dead imports.** `goimports -l ./...` is empty, or `gofmt -l ./...` if goimports is not available.

5. **No TODO/FIXME referencing the removed component.** `git grep -niE '(TODO|FIXME|HACK).*(<component-name>|<old-bead-id>)'` returns nothing.

6. **Proposal satisfied.** Re-read the relevant section of `spec/proposals/<ref>.md`. The proposal's stated end state — "X is gone, Y replaces it" — must hold after your changes.

## Non-goals

- Do NOT implement new behavior. If the proposal describes a replacement mechanism, that is a separate feature bead and NOT your job.
- Do NOT refactor unrelated code along the way. Keep the diff tightly scoped to removal + the minimum reshaping of call sites.
- Do NOT reintroduce the removed behavior under a new name. Deprecation shims are a common anti-pattern; trust the proposal.
